Role investigation · Technical Support Engineer · Prismatic

Keeping Integrations Running

Before my next conversation with Prismatic, I worked out what I think this job is day to day: who files the tickets, how one integration issue moves from report to fix, where it's likely to go wrong, and what I'd build to make the next one faster. This is an outside view based on public information and the job description. I expect parts of it to be wrong, and the conversation is my chance to find out which. I've spelled out acronyms on first use, the way I would in a customer-facing article, since this page may reach readers outside engineering.

Context

Why this role matters now

4.2Bintegration executions so far in 2026, up 53% on last year
33,000workflows built inside customers' products with the embedded builder
3ways to build: code-native, low-code, and the embedded workflow builder with AI Copilot
100sof B2B (business-to-business) software companies, from startups to the Fortune 500

Prismatic sells integration infrastructure to B2B software companies. Those companies build integrations on it, and their own customers install and run them. Support helps them get each integration working, and then keep it working. A single support ticket can involve three parties: the Prismatic customer, their customer, and the third-party app at the other end of the integration.

That chain is getting longer. At Connect 2026, Prismatic demoed the embedded workflow builder with AI Copilot: the software company publishes a workflow template, and its customer starts from that template and customizes it in plain language, without writing code. The vendor controls which connectors are available, and Prismatic's security model (data isolation between customers, plus data processing agreements, or DPAs) is what makes it safe to offer. The pitch is that customers build their own automations instead of filing tickets. The workflows multiply, and more of the people debugging them didn't write them. Prismatic's own roadmap reflects this: a rebuilt execution management and debugging experience is listed under "Now." Support is also moving into Customer Engineering, next to the engineers who help customers design their integrations.

The software being connected is changing too. More of it is built for one industry, and industry-specific apps tend to become data silos unless something connects them. Prismatic's customers connect those apps to the obvious systems, like a customer's Salesforce. They also connect them to an enterprise customer's home-grown ERP (enterprise resource planning system), or to a custom database the customer built for in-house reporting. For support, the second kind is the hard kind: undocumented APIs (application programming interface, how one program requests data from another), older protocols like SOAP (an XML-based web service standard), on-premises network access, and data formats nobody wrote down.

My read: Prismatic is paying for fast, accurate answers about integrations nobody on the support team wrote, and for turning repeated questions into docs, product feedback and fewer tickets.

The job, as a sequence

One integration issue, from ticket to trend

The posting lists the work as triage, troubleshooting, collaboration with Engineering and Product, and reporting trends. In order, that's a track. Below it is what I think each stage involves, where it breaks, and what I'd improve.

Intake

Who is affected, which instance, which execution

Reproduce

A failing run next to a passing one

Isolate

Delivery, auth, data, or the third party

Resolve

Fix or workaround, in the customer's terms

Escalate

A complete case for Engineering

Close the loop

Docs, trend tags, product feedback

01Intake

What I'd do
Work out who is affected: one end user, every instance of one integration, or a whole customer. Get the instance, flow, execution ID and timestamp before anything else. Set priority by impact and whether a workaround exists, not by the tone of the ticket.
Where it breaks
"The integration stopped working" with no instance named. A non-technical end user describing a problem in a marketplace their vendor built. A production outage filed as a how-to question.
What I'd improve
An intake macro that asks for instance, flow, execution ID, and expected versus actual result, with a link showing where to find an execution ID.

02Reproduce

What I'd do
Pull the failing execution and a recent successful one for the same flow, and compare step inputs and outputs until they diverge. Rerun with the same payload in a test instance when that's safe.
Where it breaks
The failure depends on data that only exists in the customer's production account on the third-party app. Intermittent failures that don't reproduce on demand.
What I'd improve
A side-by-side view of two executions that highlights the first step where they differ.

03Isolate

What I'd do
Check layers in order of how cheap they are to rule out: did the trigger fire, is the connection authenticated, is the data the expected shape, and what did the third-party API actually return.
Where it breaks
An expired token that shows up as a data error two steps later. A third-party API that returns 200 and does nothing. A config variable set differently for one customer.
What I'd improve
A per-layer checklist kept in the knowledge base, updated every time a new failure type shows up.

04Resolve

What I'd do
Give the exact change (which step, which input, which setting) and explain it in terms of what the customer will see. Confirm the next execution succeeds before closing.
Where it breaks
The fix works for one instance while other customers on the same integration version keep failing and haven't filed yet.
What I'd improve
Check every instance on that integration version for the same error, and contact those customers before they write in.

05Escalate

What I'd do
Hand Engineering a case they can act on without asking anything: execution IDs, what I ruled out and how, the smallest reproduction I found, and how many customers it affects.
Where it breaks
Escalations bounce back with questions. Engineering can't reproduce without customer data. The customer hears nothing while it waits.
What I'd improve
The same escalation template every time, and a scheduled update to the customer even when there's no news.

06Close the loop

What I'd do
Turn anything I explained twice into a docs article or a saved reply. Tag the ticket with a root cause so patterns show up across customers.
Where it breaks
The same question gets answered twenty times in private tickets. Product hears about a pain point from sales before support.
What I'd improve
A short monthly trend summary for Product and Account Management: top root causes, affected connectors, and what would remove them.

Troubleshooting

Work through the layers, write it down, escalate cleanly

The posting names the main categories: "debugging API requests, authentication issues, and data formatting challenges." I'd check the cheapest layer to rule out first, and keep notes as I go so the escalation is already written if I need one.

Delivery

Did it arrive?

  • Trigger fired, or schedule ran in the right timezone
  • Correct webhook URL for this instance and flow
  • Endpoint security and API keys
  • Retries and duplicate deliveries from the sender
Auth

Who is calling?

  • 401 means the credentials are missing or invalid; 403 means they lack permission
  • OAuth refresh token expired or revoked
  • Scopes changed on the third-party app
  • Auth code versus client credentials; JWT (JSON Web Token) expiry and clock skew
Data

Is the shape right?

  • Content type matches the body: XML (Extensible Markup Language), JSON (JavaScript Object Notation) or CSV (comma-separated values)
  • Nesting and paths after parsing
  • Pagination that stops after page one
  • Encoding, date formats, nulls, optional fields
Third party

What did they say?

  • Rate limits and Retry-After
  • Timeouts and 5xx responses
  • API version changes and deprecations
  • A 200 response that didn't do anything

Every escalation includes the symptom, the customer and instance, the execution IDs, what I ruled out and how, and how many customers it affects.

Hands-on

What I built to learn the bonus skills

The posting lists webhooks, GraphQL and OAuth 2.0 flows as bonus experience. My professional API work has been mostly REST, so I built webhook-integration-demo to work through the rest hands-on. It's a TypeScript server that receives GitHub webhooks, verifies their signatures, skips duplicate deliveries, makes follow-up REST and GraphQL calls, and runs a full OAuth 2.0 authorization code flow. There's a live version that runs in the browser with no setup.

Signature verification is where a lot of webhook tickets start, so it's the piece I'd point a customer to first:

// src/webhooks/github.ts: reject any delivery that wasn't signed with our secret
function isValidSignature(rawBody: Buffer, signatureHeader: string | undefined): boolean {
  const secret = process.env.WEBHOOK_SECRET;
  if (!secret || !signatureHeader) return false;

  const expected = "sha256=" + createHmac("sha256", secret).update(rawBody).digest("hex");
  const expectedBuf = Buffer.from(expected);
  const actualBuf = Buffer.from(signatureHeader);

  // Lengths must match before timingSafeEqual, or it throws.
  if (expectedBuf.length !== actualBuf.length) return false;
  return timingSafeEqual(expectedBuf, actualBuf);
}

Reviewing it later, I found two bugs that are typical of real integration tickets:

  • Lost retries. A delivery is marked as seen before it's processed. If the follow-up API call fails, the sender's retry is dropped as a duplicate and the event is lost.
  • Silent failures. The REST calls don't check response.ok, so a 403 from GitHub still reports success.

Both are the kind of thing a customer would describe as "it works most of the time."

Tooling and process

What I'd build in the first 60 days

These are ideas from outside. Some may already exist. I've ordered them by how much repeated work each would remove.

Intake macro

Asks for instance, flow, execution ID, and expected versus actual result on every new ticket.

Saves the first round of back-and-forth on most tickets.

Execution compare

Shows a failing and a passing execution of the same flow side by side and highlights the first step where they differ.

"Works sometimes" tickets get solved by finding the difference, and this finds it in one view.

Connection health check

Lists connections across a customer's instances that are failing to refresh or close to expiring.

Lets support contact the customer before an expired token becomes an outage ticket.

Copilot ticket playbook

A short guide for tickets about AI-built workflows: what to check on the canvas, which template and connector limits apply, and when it's a Copilot problem.

These tickets are new, and they'll grow with the embedded workflow builder.

Escalation template

One format for every escalation: symptom, instance, execution IDs, what was ruled out, impact.

Engineering can start work without asking questions first.

Root-cause tags and trend report

Each closed ticket gets a root-cause tag, rolled up monthly into the top patterns and the docs or product change that would remove each one.

This is the posting's "identify, gather data, and communicate customer trends to internal teams."

My working method is the one I wrote up in the Hermes project and use at Atlassian with Rovo agents. I decide what a tool should do and what "correct" means, an AI coding assistant writes and audits the code, and I check the results against real data before anyone relies on them. Prismatic publishes AI rulesets and Skills for coding assistants, so I'd expect customers to use the same approach, and I'd want to understand how those tools shape the code that ends up in tickets.

A sample day

What a Tuesday might look like

This is a hypothetical day, based on the posting's "a new challenge every day."

08:00

Read the overnight queue. One customer's CRM (customer relationship management) sync has failed on 12 instances since 2 a.m., all with the same error. That points to a shared cause, so it goes to the top.

08:45

All 12 instances share one OAuth app on the CRM side, and its client secret was rotated last night. I give the customer the exact connection setting to update and confirm the next run succeeds.

10:30

A low-code builder's sync stops at 100 records. Their loop never requests page two. I show them where to use the cursor from the response, and save the answer as a draft docs article.

12:00

A ticket from a vendor whose end user built a workflow with Copilot: Slack messages go to the wrong channel. The generated step used the template's default channel. I fix it, and note the pattern for Product.

13:30

A code-native developer's import fails after an SDK upgrade. I reproduce it with the Prism CLI, find the changed function signature, and send the fix.

15:00

Escalate a timeout pattern in one connector to Engineering, with execution IDs, what I ruled out, and the three affected customers.

16:30

Tag today's tickets, publish the pagination article, and add the Copilot channel issue to the monthly trends.
